# Contributing to scrapescope

Thank you for helping. This guide covers what the project accepts, how to set
up and test, and how to contribute catalog entries with evidence.

Security problems go to [SECURITY.md](SECURITY.md), not to public issues.

## How changes are accepted

- The ipvolt team reviews and merges every change and answers for what is
  merged.
- History is kept truthful: commits are not rewritten or squashed to remove
  authorship, and co-author trailers (including those for AI assistants) stay.
- If you used an AI assistant for a contribution, say so in the pull request.
  You remain responsible for the change, and you should understand every line
  of it.
- Contributions are accepted under the MIT licence of this repository.

## What fits, and what does not

scrapescope measures and explains where a job's proxy bytes go. It stays
neutral between providers and stays local.

Welcome: measurement accuracy, new client coverage, clearer reports, fixes for
the documented limits, better tests and fixtures, catalog entries with
evidence, documentation corrections.

Not accepted, whatever the implementation quality:

- features that help get past anti-bot systems: challenge or CAPTCHA solving,
  fingerprint spoofing, stealth patches, token harvesting or replaying captured
  session state;
- TLS interception or origination;
- telemetry, analytics, crash reporting, update checks, or any network call
  that is not the user's job, `find`'s page load or the single `--verify`
  request;
- a default provider, rate or account, affiliate links, or rankings of
  providers;
- anything that puts bodies, cookies, header values, credentials, query
  strings, the upstream address or `find` values into reports, logs or the
  events file.

## Development setup

scrapescope needs Python 3.11 or newer. The test suite has run on macOS with
Python 3.12; Linux is expected to work but not yet tested, and Windows is
untested in v1. `.github/workflows/ci.yml` runs the suite on Linux and macOS
with Python 3.11 to 3.14 on every push and pull request.

Clone the repository, then, with any Python 3.11 or newer (`python3.12` here
is an example):

```sh
git clone https://github.com/ipvolt/scrapescope.git
cd scrapescope
python3.12 -m venv .venv
.venv/bin/pip install -e '.[browser,dev]'
.venv/bin/python -m playwright install chromium
```

## Tests

```sh
.venv/bin/python -m pytest                     # everything
.venv/bin/python -m pytest -m 'not browser'    # without Chromium
SCRAPESCOPE_SKIP_BROWSER_TESTS=1 .venv/bin/python -m pytest
```

Playwright is an optional extra, so everything not marked `browser` must also
pass with only `.[dev]` installed, as in CI's "without a browser" job:
`tests/test_packaging.py` runs such tests with Playwright made unimportable
(`-p tests._no_playwright`). A test that fakes `find` should not depend on the
package; one that imports Playwright itself should use
`pytest.importorskip`.

- **No test touches the internet or real DNS.** The fixtures in `tests/fixtures`
  run a local test world: HTTPS origins with fake hostnames (`origin-a.test`, a
  fake `api.openai.com`, locally served Chromium background hosts), and HTTP
  CONNECT and SOCKS5 upstreams that resolve those names only through a hosts
  map and count bytes on their side of the socket. Read
  [tests/fixtures/README.md](tests/fixtures/README.md) before writing tests.
- TLS uses a local test CA: httpx and Requests get the CA file, curl gets
  `--cacert`, and Chromium runs with `ignore_https_errors=True` in tests only.
- Tests that need Chromium are marked `@pytest.mark.browser` and skip cleanly
  when it cannot launch.
- Every test has a timeout (60 s by default; mark longer ones with
  `@pytest.mark.timeout(120)`).
- Tests that exercise a new output or error path should also check the
  credential sentinels (the distinctive fixture username and password, and
  their Basic base64 form) are absent from every output.
- The fixture world speaks HTTP/1.1 only. HTTP/2 behaviour is covered by
  `tests/test_helpers_playwright_h2.py`, which starts a small Node.js
  `node:http2` origin and is skipped when `node` is not installed, and by
  `tests/test_helpers_hooks_h2.py` (HTTPX with `http2=True` against that
  origin), which also needs the `h2` package from the `dev` extra.
- The golden reports in `docs/dev/` are generated by
  `scripts/make_example_reports.py` through the real builders, and a test
  compares them with a fresh build. After changing a generator, a fix or a
  report field, run `python scripts/make_example_reports.py --write`.

## Code style

- `from __future__ import annotations`, type hints, small focused modules.
- Docstrings state accuracy limits honestly; figures are "tunnel-measured",
  "allocated", "hook-reported" or "estimated billable transfer", never "exact"
  outside the method notes.
- Source files are ASCII; write non-ASCII characters as `\uXXXX` escapes.
- Core dependencies are `h11` and `httpx[socks]` only. Playwright (the
  `[browser]` extra) and Requests are imported lazily inside functions, so
  `import scrapescope` works without them.
- Pass every untrusted string (hostnames, paths, catalog text, anything from
  the network or the events file) through the sanitisers in
  `scrapescope.types` before printing or writing it.
- Never log or print the upstream URL, credentials or `Proxy-Authorization`.
- Module interfaces and data shared between modules are defined in
  [docs/dev/contracts.md](docs/dev/contracts.md) and `src/scrapescope/types.py`.
  Change them there first.
- A change to report.json fields is a schema change: update
  `src/scrapescope/report/schema.json`, regenerate the example reports in
  `docs/dev/` (`python scripts/make_example_reports.py --write`), and update the
  renderers and [docs/privacy.md](docs/privacy.md).
- When behaviour changes, update the documentation and the
  [claims to verify](docs/method.md#claims-to-verify) table.

## Catalog entries

scrapescope ships three versioned JSON catalogs in `src/scrapescope/catalog/`.
They are the part of the project where outside knowledge helps most, and the
part where a wrong entry misleads users most, so every entry needs public
evidence and the maintainer reviews each one.

For every catalog change:

1. Edit the entry and set the file's `version` to the date of the change,
   `YYYY.MM.DD`.
2. Run the tests. The catalog loader validates every file (ids, host globs,
   regular expressions), and reports record each catalog's version.
3. In the pull request, give the evidence described below and say how you
   checked it.

Ids are lowercase `[a-z0-9][a-z0-9_-]{0,63}` and unique per file. Host globs
are lowercase `[a-z0-9_.:*-]`, where `*` matches any characters including dots
and `*.example.com` does not match `example.com`. Keep globs as narrow as the
evidence allows.

### background.json: traffic the browser starts by itself

An entry names hosts that a browser engine contacts on its own (component and
extension updates, model downloads, Safe Browsing lists and similar), not
because a page or the job asked for them. A host matching an entry is labelled
`background:<id>`. An unlisted host is never called background; it lands in
`unattributed`. That is deliberate: a wrong background label hides real page
traffic.

Does not qualify: ads, analytics and trackers that pages load (those are page
requests and are attributed to the page), CDNs, hosts you simply do not
recognise, and traffic from extensions you installed yourself.

Fields:

```json
{
  "id": "optimization-guide",
  "hosts": ["optimizationguide-pa.googleapis.com"],
  "component": "Chromium optimisation guide model downloads",
  "evidence": [
    "https://blog.skyvern.com/how-we-accidentally-burned-through-200gb-of-proxy-bandwidth-in-6-hours/",
    "https://github.com/nodemaven/proxy-benchmark/blob/main/NOTEBOOK.md#chrome-pays-its-vendor-43-mb-per-profile-and-the-pool-was-billed-for-it"
  ],
  "host_evidence": {
    "optimizationguide-pa.googleapis.com": [
      "https://blog.skyvern.com/how-we-accidentally-burned-through-200gb-of-proxy-bandwidth-in-6-hours/",
      "https://github.com/nodemaven/proxy-benchmark/blob/main/NOTEBOOK.md#chrome-pays-its-vendor-43-mb-per-profile-and-the-pool-was-billed-for-it"
    ]
  },
  "credits": ["NodeMaven, measured 2026-08-19: ...", "Skyvern postmortem: ..."],
  "security_tradeoff": "What blocking this host costs the browser, stated plainly.",
  "last_verified": "2026-09-23"
}
```

- `evidence`: every public URL the entry relies on, showing the host is
  contacted by the browser itself: Chromium source or documentation, a bug
  tracker issue, or a published measurement. Credit whoever found it first in
  `credits`, and put the credited source's URL in `evidence`.
- `host_evidence`: for every host glob in `hosts`, the URLs that name that host
  (each one also listed in `evidence`). The loader's strict check
  (`check_documents`) rejects an entry where a host has no evidence of its own,
  so a glob cannot ride on another host's source. Keep globs as narrow as that
  evidence: `*.gvt1.com` is listed because Google's documentation names the
  domain, not because one download host was seen.
- `security_tradeoff`: what blocking it costs. For example, component updates
  also deliver certificate-revocation lists and Safe Browsing data, so blocking
  them weakens the browser's protections.
- `last_verified`: the date you last saw the behaviour, `YYYY-MM-DD`.

In the pull request, also include a reproduction:

- the browser, its version, the operating system, the launch flags, and whether
  the profile was fresh or persistent;
- steps that trigger the traffic without any third-party target, for example a
  browser left on `about:blank` or a local page, run under
  `scrapescope run --direct` with the Playwright helper;
- an excerpt of the resulting report: the `hosts[]` entry for the proposed host
  (it should show `requests: 0` and land in `before_attach` or `unattributed`
  before your change) and the totals. Do not share the rest of the report if
  it names your own targets.

### challenges.json: recognising challenge pages

`find` uses these signals to recognise a challenge or block page, so that it
reports "blocked; cannot search" instead of "not found". They classify
responses only. Contributions that help get past a challenge are not accepted.

```json
{
  "id": "cloudflare",
  "name": "Cloudflare",
  "source": "Cloudflare documentation",
  "signals": [
    {"type": "header", "name": "cf-mitigated", "pattern": "^challenge$", "statuses": [], "strength": "challenge",
     "sources": ["https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/"],
     "note": "optional: how this rule differs from its source"}
  ],
  "docs": ["https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/"]
}
```

- Every signal lists its own `sources`: https URLs of pages that contain that
  signal (vendor documentation, or another project's rules file). The strict
  check rejects a signal without them. Use `note` when the rule narrows its
  source, for example by adding a status restriction.

- Signal types: `header` (name, optional value pattern), `cookie` (a
  `Set-Cookie` name glob, optional value pattern), `status` (a list of
  statuses) and `body` (a pattern over the first 64 KiB of the decoded body). A
  non-empty `statuses` list additionally restricts any signal to those
  statuses. Patterns are Python regular expressions applied with `re.search`;
  header and body patterns are case-insensitive (see
  [docs/dev/contracts.md](docs/dev/contracts.md), section 8).
- `strength`: `challenge` makes the response count as blocked; `vendor` only
  names the vendor. A signal that also fires on ordinary pages (a vendor's
  always-present script path, a bot-management cookie) must be `vendor`
  strength or be restricted with `statuses`.
- Evidence: the vendor's own documentation in `docs` and the signal's
  `sources`, or another project's patterns under a compatible licence, named in
  `source`, listed in the signal's `sources` and credited in [NOTICE](NOTICE)
  (which also carries that project's copyright and licence notice).
- Keep patterns simple and bounded: no nested quantifiers that can backtrack
  catastrophically on a 64 KiB body.
- Add a test with a synthetic response that fires the signal, and one with an
  ordinary page that does not.

### direct.json: hosts that never go through a paid proxy

Under `run --env-all`, hosts in this file (LLM APIs) are connected directly,
from the user's own IP address even when a provider is configured, and
reported as "non-target", because sending a job's model calls through a per-GB
proxy changes the job and bills the user for traffic they never meant to proxy.
Cloud-storage hosts (S3, GCS, Azure Blob, R2 and similar) are not accepted:
buckets are often scrape targets, and carrying them direct would expose the
user's IP address to the bucket owner.

```json
{"id": "anthropic", "hosts": ["api.anthropic.com"], "reason": "LLM API"}
```

Include in the pull request a link to the service's official API
documentation showing the hostname, in the entry's `docs`. Entries are for API
endpoints jobs call as clients, never for hosts that serve content people
scrape. Prefer exact hostnames; a wildcard is acceptable only when every name
under it belongs to the API provider (such as `*.openai.azure.com`). An entry
may list an older host its current SDK no longer uses when a still-supported
SDK does: `together` lists `api.together.ai` (the current SDK and docs) and
`api.together.xyz` (the deprecated v1 Python SDK).

One documented exception to "never hosts people scrape": OpenRouter serves its
API (`openrouter.ai/api/v1`) on the same host as its website, and host rules
cannot tell paths apart, so under `--env-all` requests to `openrouter.ai` web
pages also leave direct from the user's IP address and are not metered. The
file's `notes` state this; do not add another such host without the same
statement.

### Review checklist for catalog changes

- The evidence is public and supports exactly the hosts listed.
- Globs are no broader than the evidence.
- background: the traffic is browser-initiated, and the trade-off is stated.
- challenges: the signal cannot fire on ordinary pages at `challenge` strength;
  a test covers both cases; attribution is present where patterns were adapted.
- The file's `version` was updated and the tests pass.

## Documentation

Documentation lives in [README.md](README.md) and `docs/`. It follows the same
rules as the tool: no claims that are not measured or sourced, no "first",
no "save X%" claims (what-if figures say "would remove about X (Y% of this
run, modelled)"), and figures labelled as described in
[docs/accuracy.md](docs/accuracy.md). When you describe another project, say
what it does before what scrapescope adds, and cite its own documentation with
the date you read it.

## Before a release

Run `python scripts/release_check.py` and follow
[docs/dev/release-checklist.md](docs/dev/release-checklist.md). Catalog URLs
are checked with network access as a separate step:
`SCRAPESCOPE_CHECK_CATALOG_URLS=1 python -m pytest tests/test_catalog.py -k
still_name_their_hosts` fetches every direct.json `docs` URL and every
background.json `host_evidence` URL and checks that each page names its host.
`release_check.py` reads every file the wheel and sdist ship. It fails while
any placeholder remains (the maintainer-name placeholder, for example), while
the README has relative links (they break in a PyPI long description; the
package is installed from GitHub for now, where relative links work, so this
item stays open until the planned PyPI publication), and while
`pyproject.toml` has no project URLs or the User-Agent has no contact URL.
Text that describes a placeholder names it in words, as this paragraph does,
so that the check does not flag its own documentation.
`SCRAPESCOPE_RELEASE_CHECK=1 python -m pytest tests/test_packaging.py` runs the
same gate as a test.
